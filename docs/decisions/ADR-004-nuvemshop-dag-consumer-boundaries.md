## Context and scope

ADR-003 was ratified as `HUMAN RATIFIED — LIMITATION_AND_PRESENCE_ONLY_DIRECTION`. It establishes `orders` as owner of a future durable presence-only projection, does not authorize implementation or DAG changes, leaves `T03-GENERAL` pending, and leaves global absence blocked. NUV-12-PARTIAL is deployed subset behavior; it is not NUV-12-FULL. See [ADR-003](ADR-003-nuv-12-cobertura-integral.md#direção-arquitetural-ratificada--sem-autorização-de-implementação), especially its clauses 1–5.

The existing plan makes full NUV-12 a prerequisite of NUV-22, NUV-23 and NUV-24, while NUV-25 separately requires actual consumer evidence. This proposal changes three task prerequisites from `12-FULL` to `12-PARTIAL` and adds an explicit human activation gate before those substitutions can become effective. It also makes the retained FULL/T03/global-absence and all-18 closure obligations at 25 explicit, while preserving the existing consumer sequence `NUV-24 → catalog → identity → orders`. These clarifications are recorded in the graph companion; they do not add a dependency from NUV-25 back to consumer implementation. D1–D5 must all be approved and the exact approved text materialized before the proposed task prerequisites are effective. No task is marked complete or released now.

The graph and dependency matrix, including current and proposed Mermaid diagrams, every task/gate node, edge delta, topological order, and formal checks, are maintained in the companion artifact [NUV-DAG-01 graph and evidence](../../tasks/nuvemshop/NUV-DAG-01-graph.md). That artifact is authored separately. This ADR is the decision record; it does not duplicate or override its graph mechanically.

## Decision proposed

Recommend alternative B: distinguish (a) the deployed partial adapter capability, (b) the blocked integral adapter obligation `NUV-12-FULL / T03-GENERAL`, (c) a future `orders`-owned presence-only capability, (d) honest integration/security evidence, (e) the operational adapter milestone NUV-24, and (f) full consumer and SPEC closure NUV-25. Reuse the already-defined NUV-24 and NUV-25 milestones; do not create another milestone.

After, and only after, all D1–D5 are approved and the approved amendments are materialized, replace exactly these three dependency meanings:

No other task prerequisite is removed. The graph also makes retained obligations explicit: `T03-GENERAL`, FULL-contract/global-absence evidence, and all 18 criteria remain closure prerequisites for NUV-25; a human `DAG_EFFECTIVE` gate follows joint D1–D5 approval and exact materialization; and the already documented future consumer sequence remains `NUV-24 → catalog → identity → orders`. These are closure/activation and consumer-order clarifications, not permission to implement now. In particular, `{11,06}→{12,13}` remains as written: NUV-13 does not acquire a NUV-12 dependency. NUV-13 has independent email search, exact comparison, incomplete-result, identity, and handoff obligations. Eligibility to work locally cannot authorize a complete account order list. ## Evidence and consumer contract proposed

These are conceptual planning labels, not an approved API or TypeScript enum. They must remain distinguishable in the consumer's behavior and evidence, whether later implementation uses these labels or another approved representation.

| Concept             | Meaning and permitted consequence                                                                                                                                                                                                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PRESENCE_VERIFIED` | An exact, unique canonical `Order.number` in a sufficient current NUV-12-PARTIAL response can establish observed presence from that response. A durable index row has a stronger ingestion requirement: exact `getOrder` revalidation, store-scoped and matched to the recorded provider order ID. Record which evidence origin applies. Neither origin proves collection coverage. |
| `LOOKUP_INCOMPLETE` | Coverage was not established, including the current adapter's `NuvemshopLookupIncompleteError`, missing presence row, unfinished/stale reconciliation, provider limit, or recoverable gap. It cannot be presented as absence.                                                                                                                                                       |
| `ABSENCE_UNPROVEN`  | No current presence proof exists. This is an internal/evidence description, not a negative answer or public result.                                                                                                                                                                                                                                                                 |
| `LOOKUP_INVALID`    | Locally invalid canonical input detected before any I/O. Preserve the existing validation error distinction.                                                                                                                                                                                                                                                                        |
| `LOOKUP_FAILED`     | Transport, authorization, provider, operational, or malformed protocol response failure. Preserve `NuvemshopProtocolError` as the cause for malformed provider data; do not relabel it as local input invalidity.                                                                                                                                                                   |

The five labels describe two orthogonal dimensions: evidence state (`PRESENCE_VERIFIED` versus `ABSENCE_UNPROVEN`) and lookup-attempt outcome (`LOOKUP_INCOMPLETE`, `LOOKUP_INVALID`, `LOOKUP_FAILED`). They must not be collapsed into one total enum where a failed attempt appears to establish a fact about the order. `LOOKUP_INVALID` is only pre-I/O local validation; malformed response is `LOOKUP_FAILED` with protocol cause. `null` from the PR #50 subset remains scoped to that adapter result and is not global absence. There is no reachable state that certifies global absence under current provider evidence.

Future `orders` ownership remains consistent with ADR-003. Any later design must decide, under its own approval, canonical decimal strings (never lossy JavaScript numbers), store-scoped uniqueness for `(store_id, number)` and `(store_id, order_id)`, `getOrder` revalidation, duplicate/changed-number quarantine, reconciliation and gap recovery, idempotency, freshness, retention, RLS and minimum data. Absence of a row, completed backfill, stable counts, consecutive Links, or quiet webhooks do not prove absence. The NUV-16 webhook receipt/lease ledger is not this index.

`identity` must separately establish authenticated session, verified email, explicit order association and disclosure authorization. `/rastreio` always requires proof of possession: its authenticated path uses a session with verified email; its no-login path requires a cryptographically random one-use challenge emailed to that address, bound to that email and order, with short expiry, send/attempt limits, invalidation on success/expiry/replacement, and no plaintext storage or logging, as required by SPEC §10. PRD requires email plus order number and rate limits. The commercial number alone is not proof of ownership. `Order.contactEmail` is server-only PII. Neither incomplete search nor absent index row may conclude that an identity has no order or authorize disclosure.

`/rastreio` remains restricted to an authorized summary, fulfillment timeline and shipment tracking when available. It must not expose address, contact email, line items, prices, payment, NF-e, or raw provider data. `/conta/pedidos` must represent found results separately from a complete list; partial data, incomplete search and unreconciled index must not be shown as a complete list. NUV-13's email coverage and `orders` coverage remain independent; a number index does not certify `contactEmail` coverage.

Fiscal constraints remain unchanged: legacy NF-e is `UNVERIFIED / DEFERRED_PROVIDER_EVIDENCE_REQUIRED`; modern-only data remains `incomplete`, including an empty result; `not_consulted` is distinct from absence; malformed present data remains a protocol error. No DAG change or naming change waives NUV-11-LEGACY-B, NUV-23's tests, or NUV-25's consumer proof.

Alternative A is a defensible hold if humans reject the proposed split. It does not create an executable path to 24 if `12 complete` semantically requires the future `orders` consumer, which itself follows 24. A literal acyclic graph does not settle this semantic dependency. Alternative B resolves that ambiguity without claiming completeness. Alternative C is unnecessary because current plan already defines `ADAPTER OPERATIONAL / SPEC CLOSURE PENDING CONSUMERS` for 24 and `IMPLEMENTATION COMPLETE` only for 25; retain those boundaries rather than multiplying milestone names.

## Consequences and non-effects

If all five decisions are approved and exactly materialized, 22 and 23 may produce their already-required bounded security and mock-integration evidence using the partial adapter contract; 24 may establish only its existing operational adapter milestone after every other task and operational gate passes. No such readiness exists today. D1–D5, later implementation authorization, all task owners' evidence, PR release approval, and task-specific external authorizations remain distinct.

NUV-12-FULL remains `ARCHITECTURAL_ADJUDICATION_REQUIRED`; T03-GENERAL remains `PENDING_COVERAGE_EVIDENCE`; `GLOBAL_ABSENCE` remains `BLOCKED_COVERAGE_EVIDENCE`. NUV-25 is not advanced. No provider contract is inferred and no code, migration, worker, consumer, secret, OAuth scope, CI workflow, or infrastructure is changed by this proposal.
